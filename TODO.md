# Candidate Profile Service: Implementation Plan

Work through these in order. Each one is small enough to finish and check before you move on. Search the code for `TODO <n>` to find where each step goes.

After every step, `npm run typecheck` should still pass and `npm run dev` should still start.

## Phase 1: Infrastructure

### TODO 1: Validate environment configuration ✅ Done
**Files:** `src/config/env.ts`

Right now, missing or malformed variables fall back to defaults without any warning (`Number("abc")` becomes `NaN`, for example). Make the service **fail fast** on bad config:
- Decide which variables are required and which can have safe defaults.
- Check that the ports are valid port numbers.
- Throw one clear error that lists everything that is wrong.

**Done when:** starting with `REST_PORT=abc` stops immediately with a readable message.

### TODO 2: Configure the PostgreSQL (Supabase) connection ✅ Done
**Files:** `src/config/database.ts`, `src/server.ts`, `.env`

SSL and the connection string are already wired up. You still need to:
- Put your Supabase **Session pooler** connection string in `.env` (see `.env.example`).
- Set sensible `Pool` options (max connections, timeouts). Supabase limits connections per project, so keep `max` small.
- Add a listener for the pool's `error` event.
- Implement `checkDatabaseConnection()` so it runs a trivial query and logs success.
- Call it from `main()` in `server.ts`. Decide whether an unreachable DB should stop startup or only log a warning, and be ready to justify that choice.
- *(Recommended)* Download Supabase's CA certificate and set `DATABASE_SSL_CA_PATH`, so the server certificate is verified.

**Done when:** `npm run dev` logs a successful connection to Supabase, and a wrong password gives the behaviour you chose.

### TODO 3: Design the candidate profile schema ✅ Done

> Tables were created in the Supabase dashboard (`001_init.sql`), then adjusted in `002_small_schema_fixes.sql` and `003_match_frontend_profile.sql` so they store exactly what the frontend sends. The Supabase Data API is turned off, so the database is only reachable through this service.

**Files:** `db/migrations/`

Tables: `candidate_profile` (main row, with `verified` = confirmed from a resume) plus `candidate_skill`, `work_experience`, `project`, `education` and `job_preference`, all linked by `candidate_id` → `candidate_profile.id` with `ON DELETE CASCADE`.

If you change the schema later, add a new numbered file instead of editing one that has already been applied.

### TODO 4: Model profile types in TypeScript ✅ Done
**Files:** `src/types/profile.types.ts`

> The types follow the frontend contract (`rolefit-frontend/src/lib/types.ts`), so the REST API returns what the frontend expects without changing it. Key decisions:
> - A profile's `id` is generated by this service; other services link to it as `candidateId` (see migrations 004 and 005).
> - One nested `CandidateProfile`. `ProfileData` holds the fields a candidate or the AI can fill in.
> - `initials` and `completeness` are calculated when reading, not stored.
> - Resume import does **not** save anything. It returns an `ExtractedProfile`, and confirming it saves the profile with `verified = true`.
> - `UpdateProfileInput` is `Partial<ProfileData>`: only the fields sent change, and a list replaces the old list as a whole.
> - Dates are `'YYYY-MM-DD'` strings; `education.year` is free text.

## Phase 2: Data access

### TODO 5: `ProfileRepository.findById()` ✅ Done
**Files:** `src/repositories/profile.repository.ts`

- `candidateId` = `candidate_profile.id`, generated by this service when a profile is created. Other services link to it; the child tables reference it with `candidate_id`.
- A profile is spread over 6 tables. Decide how to load the child rows: separate queries or JOINs?
- Write **parameterized** queries (`$1`), never string concatenation.
- Write a row→domain mapping function. Watch out for:
  - SQL `NULL` → `''`, `[]` or `undefined`, depending on the type
  - pg returns `numeric` columns (e.g. `minimum_salary`) as **strings**
  - `date` columns should become `'YYYY-MM-DD'` strings
  - `end` missing ↔ `is_current = true`
- Calculate `initials` and `completeness`. How to score completeness is your choice.
- Return `null` when nothing is found. The repository doesn't decide whether "not found" is an error; the service does.

**Done when:** you can call it from a temporary script or a test and get a profile or `null`. You'll need a row in Supabase to test against; insert one by hand in the SQL Editor.

### TODO 6: `ProfileRepository.saveConfirmed()` ✅ Done
**Files:** `src/repositories/profile.repository.ts`

Overwrites an existing profile with confirmed resume data and sets `verified = true`, all in one transaction, reusing the `replace...` helpers from TODO 7. Returns `null` when the id doesn't exist.

### TODO 6b: `ProfileRepository.create()` ✅ Done
**Files:** `src/repositories/profile.repository.ts`

Insert a new `candidate_profile` row with `name` and `email` from registration. Let the database generate the id (`INSERT ... RETURNING id`), then return the new profile, e.g. via `findById`. The lists start empty, so no child rows are needed.

### TODO 7: `ProfileRepository.update()` ✅ Done
**Files:** `src/repositories/profile.repository.ts`

- Change **only the fields present** in `changes`. A list that is present replaces the old list; a missing list stays untouched.
- Bump `updated_at`.
- Build the partial UPDATE safely. Column names can't be `$1` parameters, so only allow a fixed set of known columns.
- Use a transaction here too if more than one table changes.
- Return `null` when the profile doesn't exist.

## Phase 3: Business layer and REST

### TODO 8: Domain errors and HTTP error mapping ✅ Done
**Files:** `src/utils/errors.ts`, `src/middleware/error.middleware.ts`

- Add error classes for the cases your service needs, at least "profile not found" and "invalid input", each with an HTTP status and error code.
- In the middleware, handle malformed JSON bodies (Express raises its own error for those) and make sure DB errors never leak SQL or stack traces to clients.

### TODO 9: `ProfileService.getProfile()` ✅ Done
**Files:** `src/services/profile.service.ts`

Use the repository, and throw your not-found error (TODO 8) when there's no profile. Also decide whether an unverified profile should be returned to everyone. Job Discovery also calls this method via gRPC.

**Done when:** `GET /api/profiles/<id>` returns 200 for an existing profile and 404 otherwise.

### TODO 10: Validate REST input in the controller
**Files:** `src/controllers/profile.controller.ts` (optionally a new helper in `src/utils/` or `src/middleware/`)

The controllers currently trust `req.body` with a type cast. Add validation for each route: required fields, types, empty strings, allowed values (e.g. `EmploymentType`). Throw your validation error from TODO 8. Hand-written checks are fine. A schema library such as zod is optional.

Keep **business rules** in the service. The controller only checks that the request is well-formed.

### TODO 11: `ProfileService.updateProfile()` ✅ Done

> Decision: an empty update (`{}`) is allowed. It changes nothing except `updated_at` and returns the profile.

**Files:** `src/services/profile.service.ts`

Apply the candidate's changes via `repository.update()` and throw not-found when it returns `null`. Business rules to think about: what happens with an empty update? Should editing a verified profile keep `verified = true`?

**Done when:** `PUT /api/profiles/<id>` updates the profile and returns it.

### TODO 11b: `ProfileService.createProfile()` and `POST /api/profiles` ✅ Done
**Files:** `src/services/profile.service.ts`, `src/controllers/profile.controller.ts`

The frontend calls this when a candidate registers, and keeps the returned `id` for all later calls. Validate the body in the controller (`name` and `email` must be non-empty strings), then call `repository.create()` in the service.

**Done when:** `POST /api/profiles` with `{ "name": ..., "email": ... }` returns **201** with the new profile and its generated `id`, and `GET /api/profiles/<that id>` finds it.

### Delete: `DELETE /api/profiles/:candidateId/skills/:skillName` ✅ Done

> Removes one skill (case-insensitive) and returns **204 No Content**, or **404** if the candidate doesn't have it. Whole profiles can't be deleted on purpose: other services (Job Discovery, applications) reference the `candidateId`, so removing the candidate would leave them pointing to nothing. Only individual profile items are deletable.

## Phase 4: Resume import (AI Model Adapter)

### TODO 12: AI adapter contract
**Files:** `src/adapters/ai/ai.types.ts`

The contract is set: `parseResume()` takes the uploaded file and returns a `ParsedResume`, which is the same as `ProfileData`. What's left is to decide how an adapter handles what the AI misses or gets wrong: empty values, invalid `EmploymentType`s, badly formatted dates. Write that rule down as a comment, because every adapter (fake and real) must follow it.

### TODO 13: Fake `parseResume()` for development
**Files:** `src/adapters/ai/ai.adapter.ts`

Make `PlaceholderAIModelAdapter.parseResume()` return a fake but realistic `ParsedResume`, so you can build the import flow with **no** real AI call. The frontend's `extractedResumeSample` in `rolefit-frontend/src/lib/mock/candidates.ts` is a good template.

### TODO 14: `ProfileService.importResume()`
**Files:** `src/services/profile.service.ts`, `src/controllers/profile.controller.ts`, `src/routes/profile.routes.ts`

The frontend uploads a **file** (`importResume(file: File)`), so:
- Add an upload middleware such as multer to the `import-resume` route, and build the `ImportResumeInput` (file name, MIME type, content) in the controller.
- Decide which file types and sizes you accept.

The service then calls `aiModelAdapter.parseResume()` and returns an `ExtractedProfile`. **Nothing is saved yet.** Also consider: what if the adapter fails or returns unusable data? Which error and status code should the client get?

**Done when:** uploading a file to `POST /api/profiles/import-resume` returns extracted data.

### TODO 15: `ProfileService.confirmExtractedProfile()` ✅ Done

> Confirm works (`POST /api/profiles/:candidateId/confirm`). The import step before it is still TODOs 12–14.

**Files:** `src/services/profile.service.ts`, `src/controllers/profile.controller.ts`

Route: `POST /api/profiles/:candidateId/confirm` with `{ "profile": { ...reviewed data... } }`. The profile was already created at registration (TODO 11b), so confirm always overwrites an existing one via `repository.saveConfirmed()`.
- **Controller:** check that the body contains a `profile` object.
- **Service:** business rule that a confirmed profile needs a non-empty `name`; throw not-found when `saveConfirmed` returns `null`.

**Done when:** import → confirm → get works end-to-end over REST.

## Phase 5: Internal gRPC API

### TODO 16: Complete the gRPC contract
**Files:** `proto/candidate-profile.proto`, `src/grpc/candidate-profile.grpc.ts` (`CandidateProfileMessage`)

### TODO 17: Implement the gRPC `GetProfile` handler
**Files:** `src/grpc/candidate-profile.grpc.ts`

The call into `profileService.getProfile()` is already wired. You still need to:
- Validate `candidate_id` (an empty string is the proto3 default).
- Implement `toProtoProfile()` (domain → proto; watch out for `Date` values, which proto3 has no plain type for).
- Map your domain errors to proper gRPC status codes in `toGrpcError()`.

Do **not** add any business logic or SQL here. If you need a rule, it belongs in `ProfileService`.
